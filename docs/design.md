# 네이버 예약 감시 확장프로그램 설계

## 목적과 범위
사용자가 입력한 네이버 예약 상품 URL, 날짜, 우선순위 시간 목록을 감시한다. 로그인된 Chrome의 지정 탭에서 공개 화면 DOM을 확인하고 활성 시간 버튼을 발견하면 예약 진행 버튼을 클릭한다. 기본값은 진행 화면에서 중지하며 최종 신청 자동 클릭은 명시적으로 켜야 한다. 제출 버튼의 기본 식별값은 사용자가 제공한 HTML로 등록했고 사용자 선택자로 재정의할 수 있다. 성공으로 기록하는 것은 버튼 클릭이며 실제 예약 성립은 예약 내역에서 확인한다.

참고 상품: https://m.booking.naver.com/booking/13/bizes/1491414/items/7037654
실제 페이지의 동적 DOM을 Chromium에서 조사했다. 기본 달력, 오전/오후 시간 구역, 다음단계 버튼을 등록하고 마감 처리·특정 시간·전체 시간 모드를 검증했다. 로그인 이후 최종 제출은 검증하지 못했다. 자세한 근거는 [조사 기록](site-investigation.md)에 남긴다.

## 구성
- Manifest V3, 외부 라이브러리와 서버 없는 JavaScript 확장.
- 팝업: URL, 날짜, 시간 목록, 랜덤 확인 주기(기본 15~60초, 최소 5초), CSS 선택자, 자동 확정 여부 설정 및 시작/중지, 최근 10개 로그.
- 서비스 워커: 지정 탭 생성, storage.local 상태 관리, 콘텐츠 타이머와 일회성 chrome.alarms를 통한 새로고침. Promise 큐로 상태 변경을 직렬화한다.
- 콘텐츠 스크립트: 지정 탭 여부를 워커에 확인하고 DOM 준비를 기다려 날짜 → 우선순위 시간 → 예약 진행 → 선택적 최종 확정을 수행한다.
- 권한: storage, alarms, tabs, 네이버 예약 두 도메인. 로그인 토큰을 읽거나 별도 서버로 전송하지 않는다.

## 상태 및 중복 방지
대기 → 감시 → 예약 진행 잠금 → 종료. 활성 슬롯 발견 시 워커의 CLAIM으로 감시 상태를 원자적으로 예약 진행 상태로 바꾸고 알람을 제거한다. 다른 탭과 오래된 작업 ID는 거부한다. 브라우저 재시작, 탭 닫힘, 다른 경로로 이동, 오류 발생 시 중지한다. 동일 상품의 /request 페이지에서는 저장된 booking 상태를 불러와 필수 입력을 이어간다. 중복 제출을 피하기 위해 실패 시 재예약하지 않고 사람이 화면을 확인한다.

## 화면 인식
날짜는 정확한 YYYY-MM-DD data-date/aria-label 또는 명시한 CSS 선택자를 사용한다. 참고 페이지의 공개 JS 번들에서 calendar_title/calendar_table/calendar_date/num 구조를 확인하여, 연월 헤더를 읽고 최대 24회 월 이동 후 일자 버튼을 고르는 보조 경로도 구현했다. 헤더를 해석하지 못하면 클릭하지 않는다. 이 경로의 현재 월 날짜 선택은 실브라우저에서 검증했다. 다른 월 이동은 추가 수동 검증 대상이다. URL 날짜만으로 선택 성공을 가정하지 않는다. 시간은 실제 .time_area의 .btn_time을 찾고 .time_title의 오전/오후 또는 AM/PM을 반영해 HH:mm으로 정규화한다. 원하는 시간 목록 또는 모든 시간 모드로 활성 버튼을 찾으며 선택자 재정의도 지원한다. 표시되지 않거나 disabled/aria-disabled/inert 버튼은 제외한다. 후보가 여러 개면 자동 선택하지 않고 중지한다. 날짜 선택 후 .calendar_date.selected의 일자를 확인하며 closed 클래스는 마감으로 처리한다. 예약 진행은 data-click-code="nextbuttonview.request"를 우선 사용하고 해당 속성이 없는 다른 화면에서만 예약하기, 예약, 다음, 다음단계 문구를 보조 사용한다. 최종 신청은 사용자가 제공한 submitbutton.submit 버튼을 기본 식별값으로 사용한다.

## 제약과 검증 계획
Chrome 알람은 절전·탭 정지에 의해 늦어질 수 있어 정확한 초 단위 스케줄을 보장하지 않는다. 감시는 브라우저가 열린 동안만 작동한다. 캡차 우회, 세션 자동 로그인, 결제정보 입력 기능은 없다. SPA/전체 페이지 전환과 버튼 구조는 네이버 구현에 따라 선택자 조정이 필요하다.

자동 검증은 URL/날짜/시간/확정 설정 검증과 JS 구문 검사를 수행한다. 수동 검증은 로그인 후 날짜와 시간 선택자 확인, 매진 상태 반복 감시, 활성 시간 발견, 중지 및 탭 닫힘, 팝업 재열기, 브라우저 재시작, 예약 진행 후 새로고침 중단을 확인한다. 자동 확정은 승인된 실제 예약 의사가 있을 때만 수행하고 예약 내역에서 결과를 확인한다. 실사이트의 날짜·시간 선택을 콘텐츠 스크립트로 검증했다. 검증 시 다음단계 클릭 이벤트를 가로채 제출과 이동을 방지했으며, 별도 조사에서 다음단계가 로그인으로 연결되는 것도 확인했다. 로그인 이후와 확장 전체의 실예약 검증은 남아 있다.

## 0.1.1: 짧은 주기와 전체 시간
시간 목록이 비어 있으면 시간 라벨(HH:mm, h:mm, 오전/오후)을 가진 활성 버튼 중 화면에서 처음 발견한 슬롯을 선택한다. 마감/매진/불가 라벨은 제외한다. 특정 시간 우선순위는 목록을 입력하면 유지한다. Chrome alarms의 최소 주기 제약 때문에 15~29초는 지정 예약 탭의 콘텐츠 타이머로 처리하며 매번 워커가 작업 ID, 탭, 경로, 감시 상태를 다시 검증한다. 확인 작업 도중에는 새로고침하지 않는다. 30초 이상은 기존 알람을 사용한다. 탭 정지, 긴 로딩, 절전에서는 지연되므로 15초의 정밀 스케줄을 보장하지 않는다.

## 0.1.2: 복수 날짜
입력 순서대로 1~5개 날짜를 저장하며 중복 날짜는 제거한다. 현재 날짜와 dateIndex를 작업 상태로 관리한다. 다음 확인 시 startDate를 다음 날짜로 바꾸어 같은 지정 탭을 이동시킨다. 한 날짜이면 기존 새로고침을 유지한다. 한 슬롯에서 예약 진행을 잠그면 모든 날짜 순회를 중단한다. 콘텐츠 메시지와 활성 상태 확인에 현재 날짜를 포함해 이전 문서의 CLAIM/RESULT/RECHECK를 거부한다. 동일한 시간 목록을 모든 날짜에 적용한다. 날짜 선택자는 다중 날짜에서 {date} 또는 {day} 템플릿을 포함해야 하며, 기본 달력 인식은 현재 작업 날짜를 사용한다.

## 0.1.4: 필수 입력 프로필과 신청 페이지
최종 신청 화면의 `.booking_inner .form_title`에 `.necessary_text`가 있는 그룹과 HTML required/aria-required 입력을 발견한다. 항목 이름 기반 키, 타입, 옵션 값/라벨, 현재 입력값을 팝업에 제공한다. 비밀번호·파일 업로드 및 구분할 수 없는 필드는 거부한다. 필수 항목 이름이 중복되거나 값/타입이 바뀌면 재설정을 요구한다. 체크박스·라디오·일반 select·텍스트 계열과 textarea를 지원하며 복수 select 및 혼합 그룹은 직접 입력 대상이다.

프로필은 `origin + 상품 경로`별로 storage.local의 formProfiles에 보관한다. 실행할 때 해당 상품의 프로필만 job에 복사한다. 변경된 필수 항목이나 선택 불가 옵션은 대체값 없이 중지한다. React 입력은 네이티브 value setter 및 input/change 이벤트, 체크박스는 label click으로 반영하고 결과를 검사한다. 원래 참고 상품은 저장한 일반 프로필이 없을 때 제모/네이버 검색 기본값을 적용한다.

watching → booking → submitting → 종료 상태다. CLAIM에서 선택 시간도 저장한다. request 페이지는 탭, 작업 ID, 날짜, origin/경로를 검증하며 URL의 startDateTime이 있으면 선택 시간과도 비교한다. 자동 확정은 FINAL_CLAIM으로 submitting 상태를 원자적으로 저장한 후 버튼을 1회 누른다. 새 문서는 submitting 상태를 재실행하지 않는다. 페이지 이동 때문에 종료 메시지를 보내지 못해도 자동 재제출하지 않는다. 최종 클릭은 접수 성공으로 간주하지 않는다.

Node 테스트와 Chromium 로컬 재현 테스트로 사용자 제공 HTML의 옵션 입력, 다른 가게 필수 입력, 수동/자동 제출 모드, 누락 옵션 중지, 팝업 프로필 저장, 문서 이동 후 작업 재개를 검증했다. 실제 로그인 상태의 신청 화면 전체 및 서버 접수는 검증하지 않았다.

## 0.1.5: 날짜 추가와 시간 조건
날짜는 기본 한 행이며 추가 버튼으로 최대 다섯 행까지 확장한다. 추가 행 삭제 시 남은 값의 순서를 보존하고 필드 이름을 다시 붙인다. 저장한 날짜 목록이 있으면 해당 개수만 복원한다.

시간 조건은 any/exact/after/range다. exact는 네이티브 시간 선택기로 추가한 목록을 우선순위 순서로 조회한다. any는 활성 슬롯 전체, after는 timeStart 이상, range는 timeStart 이상 timeEnd 이하인 슬롯을 화면 순서대로 찾는다. 슬롯은 오전/오후 정보를 포함해 HH:mm으로 정규화한 뒤 비교한다. 종료가 시작보다 앞선 범위와 잘못된 시간은 거부한다. 이전 설정에 timeMode가 없으면 시간 목록이 있을 때 exact, 없으면 any로 복원한다.

검증은 시간 경계 포함/제외, 12시간 표기 정규화, 팝업 시간 추가/삭제/조건 저장, 날짜 추가/삭제 및 복원, 재현 DOM에서 조건에 맞는 슬롯 선택과 신청 페이지로의 작업 재개를 포함한다. 예약 서버에 실제 제출하지 않는다.

## 0.1.6: 랜덤 확인 간격

intervalMin은 5초 이상의 정수, intervalMax는 15/30/60/90/120 중 하나이며 최소 값 이상이어야 한다. 기본값은 15/60이다. 매 검사 종료 후 SCHEDULE에서 양 끝을 포함한 정수 초를 독립적으로 추출한다. 직전 값과 같아도 다시 추출하지 않는다. 이전 고정 간격 설정은 팝업에서 새 범위 설정으로 복원한다.

각 페이지 검사는 scanId와 시작 시각을 가진다. 검사에 걸린 시간을 목표 간격에서 빼고 다음 확인 시각을 저장한다. 같은 검사에서 SCHEDULE을 다시 요청하면 기존 시각을 반환한다. 콘텐츠 타이머가 RECHECK를 보내며 Chrome의 짧은 알람 제한을 고려한 일회성 예비 알람도 둔다. 워커는 상태 변경을 직렬화하고 작업 ID, 검사 ID, 날짜, 탭, 예정 시각을 확인한다. 새로고침 시 검사 ID를 바꿔 이전 타이머와 알람의 중복 실행을 막는다. 예약 진행 중에는 다시 예약하지 않는다. 새로고침이나 페이지 이동 실패는 감시를 중지한다.

Node 테스트로 범위와 경계, 반복 값 허용, 설정 검증, 중복 예약·오래된 검사 거부, 조기 새로고침 거부와 페이지 이동 실패를 확인한다. Chromium 재현 테스트로 팝업 설정 저장·복원과 15초/15초/30초 타이머 동작을 확인한다. 로딩·백그라운드 제한·절전 때문에 실제 간격은 목표보다 길어질 수 있다.

## 0.1.7: 날짜 전체 확인 후 대기와 추가 시간

SCHEDULE은 아직 다음 날짜가 있으면 검사 ID를 바꾸고 같은 탭에서 다음 날짜로 즉시 이동한다. 마지막 날짜에서만 대기 시간과 일회성 알람을 등록한다. 콘텐츠 스크립트에는 중간 날짜에서 타이머를 만들지 않도록 ok:false를 반환한다. RECHECK와 예비 알람은 예약된 대기 시간이 지난 후 첫 날짜로 이동해 새 회차를 시작한다. 예약 진행 잠금을 얻은 회차는 나머지 날짜 확인과 대기를 등록하지 않는다. 오래된 검사 메시지는 계속 거부한다.

intervalExtra는 0/15/30/45/60/90/120 중 하나다. 최소 시간 5~120초에 intervalExtra를 더한 값이 intervalMax다. 기본값은 15+45이며 +0은 고정 대기다. 대기는 회차 전체 확인이 끝난 시점부터 계산한다. 기존 intervalMax 설정은 팝업에서 추가 시간으로 환산하고 표시된 옵션으로 올림한다. 테스트는 날짜 우선순위, 마지막 날짜만 예약, 전체 대기 적용, 첫 날짜 재시작, 이전 문서 거부, 예약 진행 후 중단을 확인한다.

로그를 추가할 때 최근 10개만 storage.local에 보관하며, 팝업을 열면 기존에 저장된 긴 로그도 10개로 줄인다.

## 0.1.8: 간격 직접 입력과 오류 표시

최소 시간(5~120초)과 추가 범위(0~120초)는 정수 숫자 입력이다. 추가 범위는 기존 버튼 옵션에 제한되지 않는다. 입력 즉시 오류 문구, 빨간 테두리, aria-invalid와 setCustomValidity를 갱신하며 잘못된 값이면 감시 시작 버튼을 비활성화한다. 워커도 범위를 검증한다. 최소 5초 미만의 오류 표시와 버튼 비활성화, 5초로 수정 후 해제, 설정 저장·복원을 Chromium에서 검증한다.

## 0.1.9: 같은 문서에서 날짜 순회

중간 날짜의 SCHEDULE은 페이지 이동 대신 다음 날짜와 새로운 scanId를 저장하고 nextJob을 콘텐츠에 반환한다. 콘텐츠는 같은 문서에서 다음 날짜 버튼을 선택하며 첫 날짜부터 마지막 날짜까지 우선순위를 유지한다. 매 날짜의 고정 1.5초 대기를 제거하고 기존 달력/선택 상태 준비 확인을 사용한다. 날짜 선택 후 시간 목록 갱신 대기는 유지한다. 마지막 날짜에만 타이머와 예비 알람을 등록하며 다음 회차에서 검사 상태를 첫 날짜로 초기화하고 탭을 한 번 새로고침한다.

Node 테스트는 중간 날짜에서 탭 이동·새로고침·알람이 없고 다음 회차에만 한 번 새로고침하는 것을 확인한다. 실제 워커와 콘텐츠를 연결한 Chromium 재현 화면에서 세 날짜를 같은 문서에서 순서대로 확인하고 두 번째 날짜가 예약 가능하면 세 번째 날짜를 선택하지 않는 것을 검증한다. 실제 네이버 로그인 이후 예약 제출은 수행하지 않는다. 로그 저장·표시·기존 기록 정리는 최근 10개를 기준으로 한다.

## 0.1.10: 달력 틀과 날짜 버튼 준비 구분

기본 달력 경로는 calendar_title 존재만으로 준비 완료를 판단하지 않는다. 제목의 연·월을 해석할 수 있고 숫자 일자를 가진 실제 버튼이 보여야 하며, 목표 월일이면 목표 일자의 버튼까지 나타나야 한다. 로딩 중에는 오류 로그를 남기지 않고 최대 15초 동안 300ms 간격으로 확인한다. 월 이동 후 목표 버튼도 준비 확인을 수행한다. 버튼을 찾지 못한 회차는 RESULT로 감시를 중지하여 SCHEDULE에서 완료 메시지나 다음 회차를 등록하지 않는다.

Node 회귀 테스트와 Chromium 재현 화면에서 달력 제목 틀만 먼저 생기고 2.2초 후 버튼이 생기는 경우, 끝까지 버튼이 나타나지 않아 실패로 중지하는 경우, 날짜 우선순위와 예약 진행 중단을 검증한다. 실제 사용자 탭의 상태를 직접 관찰한 것은 아니다.

## 0.1.11: 날짜별 예약 가능 여부 로그

날짜 버튼 탐색은 표시 여부로 후보를 식별하고, 마감 여부와 비활성 상태는 별도로 확인하여 비활성 마감 버튼도 인식 실패로 처리하지 않는다. 마감·선택 불가·원하는 시간 없음은 예약 불가, 원하는 활성 시간 발견은 예약 가능: HH:mm으로 기록한다. 선택 가능 상태를 별도 로그로 남기지 않는다. 날짜와 시각은 기존 로그 구조로 붙이며 최근 10개를 유지한다. 인식 실패는 예약 불가 로그로 바꾸지 않는다.

## 0.1.14: 예약 인원과 새 식당 예약 화면

partySize는 비어 있으면 null, 입력했으면 1~100의 정수다. 비어 있으면 사이트 기본 인원을 유지하며 기본값 없이 인원이 필수인 곳은 설정을 요청하고 중지한다. 가게의 허용 범위를 벗어나거나 요청 인원이 비활성이면 대체 인원으로 예약하지 않는다.

새 식당 화면은 gbw-flow-step1과 data-gbw-step1-people/day/time 상태를 읽는다. 인원 버튼 또는 직접 입력·적용을 사용하고 실제 반영을 확인한다. 숫자로만 표시되는 영문 인원 버튼은 인원 구역 안에서만 찾는다. 달력 연월과 날짜 상태를 확인하고 오전/오후 시간 목록을 정규화한 후 기존 CLAIM을 사용한다. 요청한 인원·날짜·시간이 유지되는지 확인하고 다음 버튼을 한 번 누른 뒤 감시를 중지한다. 이 화면의 최종 신청 자동 클릭은 지원하지 않는다. CLAIM에 manualContinuation을 저장하여 새 문서에서도 입력 자동화와 FINAL_CLAIM을 차단한다. 빕스의 다음 단계처럼 연령별 인원 구성이 필요한 경우 사람이 직접 설정한다. 기존 /request 신청 화면 지원과 구분한다.

기존 count_area의 단일 인원 입력 또는 증감 버튼도 지원한다. 여러 종류의 인원 입력이 있으면 추측하지 않고 중지한다. 공개 식당 화면에서 25명·10월 16일·17:00 선택을 콘텐츠 스크립트로 검증했고 다음 버튼은 가로채서 실제 접수하지 않았다. 빕스 판교점 공개 화면은 일반 예약 1~6명과 추가 연령별 구성을 확인했다. 성인 2명 구성을 선택하고 다음 버튼을 누르면 nid.naver.com 로그인으로 연결되어 최종 신청 화면은 로그인 세션 없이 확인하지 못했다. 팝업 인원 입력 저장·복원, 범위 오류, 마감·시간 조건 제외·CLAIM 거부·기본 인원 없는 경우도 검증한다. 로그인 이후 실제 예약 접수는 수행하지 않는다.

## 0.1.15: 새 신청 화면의 필수 목록과 수동 입력 적용

사용자 제공 ExtraInputForm의 필수 role=group 제목과 aria-haspopup=listbox 버튼을 발견한다. 필드 키는 질문 문구이며 React가 만드는 임시 ID를 저장하지 않는다. customselect 값은 Select 텍스트에 표시된 현재 선택 문구이며 팝업에서 동일 문구를 입력·저장한다. 이미 일치하면 클릭하지 않는다. 일치하지 않으면 버튼의 aria-controls 또는 유일하게 표시된 listbox 안의 정확한 role=option 문구를 찾아 클릭하고 실제 선택 문구가 바뀌었는지 확인한다. 비활성·중복·누락 옵션과 여러 목록은 임의 선택하지 않고 중지한다. 공개되지 않은 닫힌 목록의 옵션은 추정하지 않는다.

INSPECT_FORM과 APPLY_FORM은 해당 상품의 /request 및 /request/link에서 지원한다. APPLY_FORM은 상품 scope 일치와 페이지 이동 여부를 검사하고 필수 입력만 적용한다. 예약 진행·최종 제출 클릭은 수행하지 않는다. 식당 manualContinuation 감시는 유지하며 사용자가 신청 화면에서 직접 적용 버튼을 누른다. 사용자 제공 네 필수 안내 구조를 재현한 Chromium에서 항목 발견, 문구 적용, 다른 상품 거부, 최종 버튼 미클릭을 확인했다. 실제 로그인된 빕스 신청 화면의 열린 목록과 최종 제출은 확인하지 못했다.

## 0.1.16: 신청 화면 필수 동의 체크박스

사용자 제공 RequestV2__checkbox_agree_all 영역의 label 안에 RequestV2__required 표시가 있는 단일 checkbox를 필수 항목으로 발견한다. HTML required가 없어도 식별하며 장식용 span의 체크 클래스 대신 input.checked를 읽는다. 사용자가 저장한 선택을 label 클릭으로 적용하고 실제 checked 상태를 검사한다. 이미 동의 상태이면 토글하지 않는다. 필수 표시가 없는 동의 영역은 이 경로로 추가하지 않는다. 저장된 선택이 없으면 기존 필수 입력 정책대로 중지한다. 이 작업은 예약 제출 버튼을 클릭하지 않는다.

팝업에서 항목을 다시 불러올 때 현재 화면의 항목을 기준으로 같은 키·타입의 저장 값을 복원한다. 새 필수 항목은 현재 값으로 추가하며 삭제된 항목은 노출하지 않아 예전 프로필이 새 동의를 숨기는 문제를 해결한다. Node 회귀 테스트와 제공 구조를 재현한 Chromium에서 동의 발견·적용·이미 체크된 값 유지·기존 프로필에서 새 항목 추가·예약 제출 미클릭을 검증했다. 실제 로그인된 서버 접수는 검증하지 않았다.

## 0.1.17: 중간 단계의 인원 구성 프로필

현재 화면의 필수 항목 불러오기는 상품 경로의 gbw-flow-step2도 인식한다. role=status와 aria-label의 수량 의미로 실제 항목 이름과 현재 숫자를 읽으며 성인·청소년 등 가게별 항목 목록을 하드코딩하지 않는다. 이 화면은 최종 /request와 별도의 stage=composition이다. 인원 구성은 상품 scope별 partyProfiles에 저장하고 최종 추가정보는 기존 formProfiles에 보관한다.

팝업은 발견한 항목만 숫자 입력으로 생성한다. 인원 구성 옵션은 선택 사항이며 합계가 총 예약 인원과 같아야 감시를 시작할 수 있다. 워커도 scope·중복 이름·정수 범위·합계를 검증한다. gbwState는 기존 날짜·시간·중간 단계를 복원하므로 감시 URL에서 제거하고 작업에 지정한 조건으로 시작한다.

콘텐츠는 날짜·시간 선택 후 다음 버튼을 누르고 최대 15초 동안 중간 단계를 기다린다. 인원 구성 제목의 총인원과 저장한 항목 집합을 비교한다. 현재 값에서 감소가 필요한 항목을 먼저 줄여 가게의 총인원 한도를 넘기지 않고, 증가가 필요한 값을 적용한다. 각 클릭마다 활성 작업과 실제 수량 반영을 확인하고, 전체 결과를 검증한 뒤 활성 다음 버튼을 한 번 누른다. 항목 변경·비활성 버튼·다른 총인원은 중지한다. manualContinuation 잠금은 계속 유지하여 최종 제출을 자동으로 실행하지 않는다.

Node 테스트로 임의 항목 이름, 합계·scope 오류, 감소 우선 적용, 이미 일치하는 값 유지, 중지 동작을 확인한다. Chromium 재현 화면에서 중간 단계의 항목 불러오기·별도 저장·합계 오류·성인 2명과 미취학 1명 적용·다음 두 단계 진행·최종 예약 버튼 미클릭을 검증한다. 실제 로그인 상태의 빕스 서버 접수는 수행하지 않는다.


## 0.1.18: 상품·단계별 수량과 옵션, 최종 신청 연결

0.1.17 이하의 manualContinuation 식당 제한과 의원 기본값을 대체한다. 새 작업은 식당의 인원 구성에서 최종 /request/link까지 이어지며, 비결제 최종 신청은 autoConfirm과 FINAL_CLAIM 1회 잠금으로 처리한다. 결제 버튼은 수동 처리한다. 예전 manualContinuation 작업은 수동 중지 방식을 유지한다.

composition.widget은 gbw-flow-step2가 없어도 N명의 인원 구성 제목과 접근성 수량 버튼이 있는 공통 영역을 찾는다. composition은 상품별 partyProfiles에 보관한다. stages는 .section_option의 제목, 항목명, 수량/체크 방식, 필수 여부로 현재 단계의 항목을 발견하고 stageProfiles[scope].stages[stageKey]에 저장한다. 상품 수량은 partySize와 별개다. formProfiles는 최종 입력을 유지하며 빈 설정도 명시적으로 지원한다.

각 단계 적용 후 STAGE_DONE은 활성 job/scan/date/tab과 저장된 단계의 일치를 검사해 적용 기록을 저장한다. 최종 화면에서 기록하지 않은 저장 단계가 있으면 중지한다. 스키마 변경은 입력 전에 검사하며, 개별 값은 변경 후 확인한다. 입력이 늦게 렌더링되면 기다린 후 검사한다. 처음 예약 버튼의 클릭 핸들러가 준비되기 전이면 실제 전환이 없음을 확인한 뒤 제한 횟수 내 재시도한다.

팝업의 불러오기 결과와 인원 입력은 불러오기 버튼 바로 아래에 표시한다. 최종 추가정보 미설정 안내는 별도 영역을 명시한다. 저장할 때 최신 저장소에서 현재 상품·단계만 병합해 다른 설정을 보존한다. 실제 사이트와 재현 검증 범위는 site-investigation-2026-10-12.md에 기록한다.

## 0.1.20: 기본 버튼 정리와 날짜·시간 자동 저장

수동 입력 적용 버튼 세 개는 접힌 보조 메뉴에 배치한다. 사전 설정 중에는 중간 단계의 별도 저장 버튼을 숨기고 저장하고 다음 버튼을 사용한다. 추가정보가 없는 화면은 추가정보 저장 버튼을 표시하지 않는다.

날짜 행 추가·삭제·입력과 시간 조건·목록 추가·삭제·범위 변경은 SAVE_SCHEDULE_DRAFT로 워커에 전달한다. 직렬화된 저장은 scheduleDraft에만 쓰며 config나 실행 중인 job을 변경하지 않는다. 팝업은 최근 날짜·시간 draft를 이전 실행 config보다 우선하여 복원한다. 미완료 입력도 복원하되 감시 시작 시 기존 검증을 수행한다. Node 워커 테스트와 Playwright 팝업 검증으로 시작 없이 저장·재열기·범위와 목록 복원·활성 작업 유지·접힌 수동 메뉴를 확인한다.

## 0.1.21: 자동 예약 목적에 맞춘 버튼 정리

팝업의 수동 적용 버튼과 이벤트 핸들러를 제거한다. 자동 예약 콘텐츠와 사전 설정의 입력 적용은 유지한다. 저장 동작은 설정 저장 하나로 통합하여 불러온 화면 종류에 따라 인원 구성·중간 옵션·최종 추가정보의 기존 저장소에 각각 기록한다. 사전 설정의 중간 화면에서는 저장하고 다음만 표시하고 최종 화면에는 불필요한 다음 버튼을 숨긴다. 저장된 단계의 보기·삭제는 접힌 관리 목록으로 이동한다.

Playwright 팝업 검증은 세 저장 영역이 서로 덮어쓰지 않고 통합 저장 버튼으로 기록되는지, 사전 설정의 다음 동작이 유지되는지, 수동 적용 버튼과 APPLY 메시지가 없는지 확인한다. 날짜·시간 자동 저장은 계속 유지한다.

## 0.1.22: 사전 설정 화면 자동 표시와 상단 진행 배너

SETUP_STAGE는 경로 기록과 함께 현재 단계 snapshot을 setup.currentStep에 저장한다. 팝업은 설정 ID·단계 키·항목 schema·총인원을 비교해 새 단계만 자동으로 표시하며 값 변경이나 다른 저장소 갱신으로 편집 중인 입력을 덮어쓰지 않는다. 설정 시작은 상품 URL을 config에도 저장하여 팝업을 다시 열면 같은 사전 설정 단계가 표시된다. 읽기 오류는 탭·설정 ID·상품 경로를 검사한 SETUP_ERROR로 전달하고 성공한 재읽기로 해제한다. 다시 읽기 버튼은 실패한 경우에 표시한다.

예약 페이지의 상태 배너는 body 맨앞에 배치하며 상단 sticky 위치, 18px 글자, 20px 여백과 높은 z-index로 표시한다. 일반 문서 흐름에 공간을 확보하며 긴 내용은 최대 높이 안에서 스크롤된다. 동일 메시지는 DOM을 다시 쓰지 않아 단계 감시 observer가 반복 작동하지 않는다. 검증은 단계 자동 갱신·재열기·편집 유지·오류 표시와 복구·배너 위치 및 크기를 포함한다. 실제 예약 제출은 수행하지 않는다.

검증은 실제 서비스 워커 코드와 브라우저 DOM을 Chrome API bridge로 연결해 두 중간 단계 → 최종 화면 자동 갱신, 팝업 재열기, 같은 schema의 감지 오류 복구, 상단 배너 크기를 확인한다. 설치된 확장 통합 검증은 이 클라우드 Chromium의 관리 정책이 unpacked extension 로딩을 차단하여 수행하지 못했다. 로컬 Chrome에서는 verify:extension으로 같은 자동 경로를 검증할 수 있다.
